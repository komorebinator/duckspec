# The checks stop taking their own word

0.10.4 closed the gaps that let verification pass without verifying. This
release is what happened when the same question was asked of the checks
themselves: not "did it report anything" but "could it have". Most of what
follows was found by counting — how many functions were read against how many
exist, how many files a step covered against how many it claimed.

## Breaking

**@Key no longer extends @File**, and so no longer carries `format` or
`permissions`. Its own subtype describes keys living in an environment
variable or a hardware token, which a file-typed term cannot represent. `path`
remains, declared on @Key itself and optional: a key that is a file has one, a
key that is not does not.

**@DuckWorkflow no longer extends @Software.** It inherited `repository`,
`platform`, `tests` and the `build`, `test`, `run` and `install` recipes, none
of which apply to a delivery procedure — and it appeared in every coverage
report as software nobody had tested. @VersioningStrategy, the same kind of
term answering the parallel question of how a version is calculated, has
extended @Term all along.

**@SoftwareComponent now extends @DesignPattern** instead of @Term, and drops
the `functions`, `signals` and `components` it re-declared. Consumers gain
`src`, `fields`, `patches` and `implicit_functions` on components — which most
were already using, and which only resolved because every component happened
to declare a `type:` pointing at a pattern that had them.

**`Token#type` is now `token_type`.** A property named `type` collides with the
framework's structural field: a value there sends `unknown-field` looking for a
term of that name, which returns an empty schema and skips the entry entirely.
A property that switches off the checking of its own neighbours is worse than
no property.

**The guideline against abbreviations in @Term names is gone.** It contradicted
the sub-project naming rule, whose own worked examples — `DuckArch`, `DuckUI` —
violated it.

**`mandatory` and `placeholder` move to @UserInterfaceElement** from the nine
and five subtypes that each declared their own. Inherited rather than
re-declared; nothing referencing them needs to change.

## What the tools were getting wrong

**`absent-function` proved almost nothing.** It matched the function's name
with a word boundary across the concatenated text of a whole folder, so a
comment, a string, a call site and an import all counted as a definition — and
`__pycache__` bytecode was read as text beside the sources, letting a `.pyc`
twelve days stale vouch for a name the code no longer had. Each candidate file
is now read on its own, and files that do not decode are skipped rather than
decoded. The name search itself stays loose on purpose: a check that tried to
recognise declarations would have to enumerate every way each language permits
one, and the first idiom it had not anticipated would be an error raised
against working code.

**A `src:` written as a list was not read at all.** Only the inline form was.
Every function beneath a list-form `src:` was left with no path, and a function
with no path is one the check skips without saying so. Borshevik now verifies
96 functions where it verified 91.

**`resolve_path` returned the first of several matching entries in silence**
while the editing operations refuse the same ambiguity. That asymmetry is how a
stale duplicate of an entire recipe survived in @DuckspecProject across five
releases: nothing that reads a path ever objected to there being two of
something. It refuses now, and names the spec as the thing at fault.

**`set_field` could not change an `id`.** An entry's first field sits on the
`- ` line, two columns left of its siblings; only the sibling column was
matched, so a second `id:` was appended below the first.

**The MCP server announced version 0.1.0** to every client for the whole of the
0.10 series, and its `term_uses` printed raw dictionary keys where the CLI
prints readable labels — while the spec promises both front ends return
identical output. The version now comes from the framework's own `version:`
field.

**`grep_terms` returns an address, not a line.** Each hit carries the `#`-path
of the element it sits in, in the form `resolve_path` and `set_field` already
accept, so a search result can be acted on instead of sending the reader back
into the file to work out whose line it was.

## `validate` has a scope

The recipe had one mode and no way to report how much of it ran. Its two
expensive steps — the guideline pass and the reading half of `verify_source` —
are model work that scales with the corpus, so in practice they were cut short
while the report still read as a completed check.

`scope: normal` (the default) runs every check and may narrow only those two to
what changed. `scope: full` covers every term file and every source file, with
no sampling. The markers now carry the difference: under `normal` a narrowed
expensive step is green and names what it covered, and under `full` the same
narrowing is red, because all of it was what was asked for.

`verify_source` lists the components in scope before reading any of them and
reports one row per component. "Read the sources and compared them" is the one
claim in the recipe nobody can check, including its author.

## Recipes that had lost something

**Three versioning strategies had dropped the requirement to ask which version
to release.** The base recipe demands an interactive prompt; overriding a recipe
replaces it whole, and none of @SemVer, @CalVer or @SequentialVersion restated
it. The rule existed exactly where nobody reads it.

**The commit-message guideline returns**, now resting on something: `release`
drafts the changelog from the log, and a contributor's pull request is a set of
commits and nothing else. Four workflow recipes still asked for a "short
descriptive message"; there is no length to fit into.

**`GitHubWorkflow#release` tagged and published unconditionally after submit**,
but submit opens a pull request rather than pushing when the author lacks write
access — so the tag would land on a commit absent from `main_branch`, and the
release would be cut from a branch without it.

**Five workspace recipes described hand-editing `~/.duckspec/settings.json`**
where the resolver has an operation for each.

**The coverage step counted six terms as software with no tests**: three
framework type definitions and three external tools nobody builds here. None
declares a `src:`, and with no path to code there is nothing to run. They are
now reported as exempt with the reason, rather than omitted — the difference
between "nothing to test" and "nobody wrote the tests" is the point of the
step.

## Sub-projects load on their own

@DuckArch and @DuckVersion never reached the root project, and @DuckUI never
reached @DuckArch. Opening any of them directly produced a spec with no base
vocabulary — thirteen to thirty-nine dangling references, and rule tables that
came back empty with no warning at all. Validating from the root said nothing,
because the root pulls all of them in. Anyone starting work inside a
sub-project, which is where work usually starts, was working blind. All six
verify clean standalone now.

## Also

@Software and @Application defined each other and so defined neither. `Folder#files`
and `Tabs#tabs` promised more than their declared types allowed. `Term#lists`
still described the format in terms of `name`, left over from the identity
migration. @ListView and @TableView had no way to say what they display.
